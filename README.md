# torrent-watchdog

Веб-сервис для отслеживания обновлений раздач RuTracker. Под наблюдение берётся ссылка на тему; сервис сохраняет текущий `info_hash`, скачивает с темы свежий `.torrent` по расписанию и показывает найденные обновления. Если включён `auto_update`, он заменяет торрент в удалённом qBittorrent: ставит старый торрент на паузу, удаляет его из qBittorrent с `deleteFiles=false`, добавляет новый `.torrent` в тот же `save_path`, восстанавливает категорию и теги и применяет выбранный режим обновления. Файлы на диске не удаляются никогда.

Версия: `0.8.0`. Полный список изменений — в [CHANGELOG.md](CHANGELOG.md).

## Запуск

Нужен только Docker и файл настроек:

```bash
curl -O https://raw.githubusercontent.com/roxelalex/torrent-watchdog/master/docker-compose.yml
curl -o .env https://raw.githubusercontent.com/roxelalex/torrent-watchdog/master/.env.example
docker compose up -d
```

Поднимутся два контейнера: сам сервис и `torrent-watchdog-flaresolverr` — свой образ FlareSolverr, без него RuTracker не отдаёт файлы (см. раздел про FlareSolverr).

Образы собираются под `linux/amd64` и `linux/arm64`, так что NAS и Raspberry Pi тоже подходят:

```text
roxelalex/torrent-watchdog:latest
roxelalex/torrent-watchdog-flaresolverr:latest
```

Из исходников — то же самое, только со сборкой:

```bash
git clone https://github.com/roxelalex/torrent-watchdog.git
cd torrent-watchdog
cp .env.example .env
docker compose up -d --build
```

В клоне репозитория Compose сам подхватывает `docker-compose.override.yml` и собирает образы локально. Чтобы и там брать опубликованные, добавьте `-f docker-compose.yml`.

Откройте веб-интерфейс:

```text
http://SERVER_IP:8096
```

Вход — форма на `/login`, логин и пароль из `.env`:

```text
admin / change_me
```

Перед постоянным использованием смените в `.env` две вещи, а не одну:

- `APP_AUTH_PASSWORD` — пароль;
- `APP_SECRET_KEY` — им подписывается cookie сессии. С дефолтным значением сессию можно подделать, не зная пароля.

`APP_AUTH_ENABLED=false` полностью отключает вход. Так можно, если сервис доступен только из доверенной сети, но порт по умолчанию публикуется на всех интерфейсах.

HTTP Basic принимается как запасной способ авторизации для `/api/*` — это удобно для скриптов, веб-интерфейс им не пользуется.

Дальше нужно указать qBittorrent и доступ к трекеру — оба на странице «Настройки».

## Настройка .env

Полный список переменных со значениями по умолчанию — в [.env.example](.env.example). Ключевые:

```env
APP_PORT=8096
TZ=UTC
DATABASE_URL=sqlite:////data/app.db

QB_HOST=http://192.168.1.10:8080
QB_USERNAME=admin
QB_PASSWORD=adminadmin

CHECK_HOUR=4
CHECK_MINUTE=0
CHECK_MAX_WORKERS=3

EVENT_RETENTION_DAYS=180
TORRENT_FILE_RETENTION_DAYS=30

APP_AUTH_ENABLED=true
APP_AUTH_USERNAME=admin
APP_AUTH_PASSWORD=change_me
APP_SECRET_KEY=change_me_random_secret

RUTRACKER_ENABLED=true
RUTRACKER_USERNAME=
RUTRACKER_PASSWORD=
RUTRACKER_COOKIE=
FLARESOLVER_ADDRESS=http://flaresolverr
FLARESOLVER_PORT=8191
```

Если меняете `APP_PORT`, docker-compose пробросит тот же порт наружу и внутрь контейнера.

`QB_HOST`, `QB_USERNAME` и `QB_PASSWORD` читаются только один раз — при создании первого клиента в пустой базе. Дальше клиенты правятся на странице «Настройки», и правка `.env` на них уже не влияет.

Доступ к трекеру и адрес FlareSolverr обычно задаются на странице «Настройки» — сохранённое там имеет приоритет над `.env`. Переменные `RUTRACKER_USERNAME`, `RUTRACKER_PASSWORD`, `RUTRACKER_COOKIE`, `FLARESOLVER_ADDRESS` и `FLARESOLVER_PORT` работают как значения по умолчанию.

Сервис должен работать ровно в один процесс uvicorn. Планировщик живёт внутри процесса, поэтому второй воркер означал бы вторую ежедневную проверку: параллельные скачивания одной раздачи и гонку при применении обновления.

## qBittorrent на другой ВМ

qBittorrent не запускается внутри `docker-compose.yml` этого проекта. Он должен быть доступен по HTTP через Web API на другой ВМ или хосте.

Не используйте `localhost` или `127.0.0.1` в `QB_HOST`: внутри Docker-контейнера это будет сам контейнер `torrent-watchdog`, а не ВМ с qBittorrent.

Настройка qBittorrent на другой ВМ:

1. В qBittorrent включить Web UI.
2. Убедиться, что Web UI доступен по IP ВМ, а не только на `127.0.0.1`.
3. Проверить порт, например `8090`.
4. На ВМ с qBittorrent открыть порт в firewall.
5. В `.env` сервиса `torrent-watchdog` указать:

```env
QB_HOST=http://192.168.1.10:8080
QB_USERNAME=ваш_логин
QB_PASSWORD=ваш_пароль
```

6. Проверить доступность с сервера:

```bash
curl -I http://192.168.1.10:8080
```

7. Если сервис запущен в Docker, проверить из контейнера:

```bash
docker exec -it torrent-watchdog sh
wget -S -O- http://192.168.1.10:8080
```

Пользователь из `QB_USERNAME` должен иметь право добавлять, удалять, ставить на паузу, запускать и recheck торренты.

Для qBittorrent 5.x сервис автоматически использует новые endpoints `stop/start`, если старые `pause/resume` недоступны.

Проверить подключение можно кнопкой `Проверить всех` на странице `Настройки` — она опрашивает все настроенные клиенты. Там же можно добавить несколько qBittorrent-клиентов и затем выбирать нужный при добавлении раздачи.

Статусы клиентов кэшируются на несколько секунд, поэтому страницы не ждут ответа от недоступного клиента при каждом открытии. Кнопка `Проверить всех` опрашивает клиенты заново, минуя кэш.

При первом запуске в пустой базе создаётся клиент `qBittorrent` из переменных `QB_HOST`, `QB_USERNAME`, `QB_PASSWORD`.

Понятия «основной клиент» нет. Каждая раздача привязывается к конкретному клиенту при добавлении; клиент из формы можно поменять на любой. В списке клиенты идут по алфавиту, и первый из них подставляется в форму добавления и служит запасным для раздач без привязки — например, добавленных до появления поддержки нескольких клиентов.

Категории qBittorrent автоматически подгружаются на странице добавления раздачи и доступны через API:

```text
GET /api/qbittorrent/categories
GET /api/qbittorrent/clients
```

Если qBittorrent недоступен, приложение всё равно запускается. `/health` покажет статус qBittorrent, а операции добавления или обновления завершатся ошибкой в интерфейсе и в `check_events`.

## Добавление первой раздачи

Под наблюдение берутся только темы RuTracker:

```text
https://rutracker.org/forum/viewtopic.php?t=123456
```

Magnet и прямые ссылки на `.torrent` не принимаются — форма и API отклонят их с подсказкой. Смысл в том, что тема остаётся постоянным адресом: с неё каждый раз скачивается свежий `.torrent`, и есть с чем сравнить состав файлов. У magnet файла раздачи нет вовсе, а его `info_hash` неизменен, так что обновление по нему не обнаружить в принципе.

Откройте `Добавить` и заполните:

- ссылку на тему RuTracker;
- категорию и теги при необходимости;
- папку загрузки — только если нужно переопределить путь категории;
- параметры `auto_update`, `recheck_after_add`, `start_after_recheck`, `add_paused`.

После добавления сервис скачает `.torrent` с темы, рассчитает `info_hash`, добавит торрент в qBittorrent и создаст первую запись истории версий.

### Папка загрузки и категория

Это не два независимых поля. У категории qBittorrent обычно есть свой путь, и пустая «папка загрузки» означает «положить туда же». Заполненная — перебивает путь категории; так поступает и сам qBittorrent, когда получает и `savepath`, и `category`.

Категория выбирается списком: видны все категории клиента и их пути, а пункт «своя категория» открывает поля для названия и, при желании, пути — категория будет создана в qBittorrent.

У категории может не быть собственного пути. Это не значит «в общую кучу»: qBittorrent кладёт такие раздачи в подпапку с именем категории внутри папки по умолчанию, то есть `lidarr` без пути означает `/downloads/lidarr`. Сервис показывает именно итоговый путь, а не путь по умолчанию. Категория, исчезнувшая из клиента, остаётся в списке с пометкой «нет в клиенте», чтобы не подмениться молча при первом же сохранении.

В форме категория идёт первой, а плейсхолдер папки показывает, куда раздача попадёт при пустом поле: `как у категории: /music` или `по умолчанию у клиента: /downloads`, если своего пути у категории нет. Путь по умолчанию не выдумывается — он берётся из `GET /api/v2/app/preferences` того клиента, который выбран в форме. У поля папки есть и подсказки: путь по умолчанию и пути всех категорий. При смене клиента список категорий и подсказки перестраиваются.

В карточке раздачи показан итоговый путь и его происхождение — `/music · из категории «music»`. Раньше там стоял прочерк, хотя файлы всё это время лежали в папке категории.

Под полем смены категории написано, что произойдёт с файлами. qBittorrent сам сообщает это настройкой `torrent_changed_tmm_enabled`: при включённой он переносит раздачу вслед за категорией, при выключенной оставляет на месте. Гадать не нужно — сервис спрашивает и говорит прямо.

## Проверка обновлений

Планировщик запускается ежедневно в `CHECK_HOUR:CHECK_MINUTE` с timezone из `TZ`. Расписание применяется при перезапуске контейнера; на странице «Настройки» оно показано, но не редактируется.

Ручная проверка — кнопка `Проверить` в реестре и `Проверить сейчас` в карточке раздачи.

Раздачи проверяются параллельно, до `CHECK_MAX_WORKERS` одновременно. Обращения к FlareSolverr при этом идут строго по очереди: браузер в контейнере один, и два одновременных вызова Cloudflare не решаются оба.

Если `info_hash` не изменился, статус остаётся `active`. Если изменился, создаётся новая версия и статус становится `update_available`.

После ночной проверки выполняется уборка: удаляются события старше `EVENT_RETENTION_DAYS` и `.torrent`-файлы старше `TORRENT_FILE_RETENTION_DAYS`, на которые не ссылается ни одна версия. Оба значения можно обнулить, чтобы отключить уборку.

## Auto update

Если у раздачи включён `auto_update`, найденная новая версия применяется автоматически:

1. старый торрент ставится на паузу;
2. старый торрент удаляется из qBittorrent с `deleteFiles=false`;
3. новый `.torrent` добавляется в тот же `save_path`;
4. назначаются прежние категория и теги;
5. применяется выбранный режим обновления;
6. торрент запускается, если включено.

Доступны два режима:

- `Скачивать только новые файлы` - режим для медиатеки. Сервис сравнивает старый и новый `.torrent`, старые файлы в новом torrent помечает как `не скачивать`, новые оставляет выбранными. `recheck` не запускается, чтобы qBittorrent не перекачивал файлы, в которые уже записаны теги.
- `Полная замена с проверкой файлов` - классический режим: добавить новый torrent и запустить recheck. qBittorrent сверит уже лежащие на диске файлы и докачает только недостающее.

Если сохранённый `.torrent` прошлой версии недоступен, сравнить состав файлов не с чем. В этом случае режим `только новые файлы` не выставляет приоритеты, а запускает recheck: иначе qBittorrent считал бы, что на диске пусто, и скачал бы раздачу заново. В журнале об этом пишется явно.

## Когда файлы удаляются

По умолчанию — никогда. Сервис удаляет торрент из qBittorrent с `deleteFiles=false`, и данные остаются на диске.

Единственное исключение включается признаком `Удалять файлы при полной пересборке` у раздачи (глобальное значение по умолчанию — `DEFAULT_DELETE_REPLACED_FILES`, по умолчанию `false`). Файлы прошлой версии удаляются, только когда сходится всё сразу:

- признак включён у этой раздачи;
- это не откат;
- состав файлов удалось сравнить;
- не совпал **ни один** файл, то есть релизёр пересобрал раздачу целиком;
- прежний торрент существует и отличается от нового.

Любое несошедшееся условие означает «не трогать». Решение принимает одна функция `may_remove_replaced_files` в `app/services/update_applier.py`, и она закрыта тестами на каждую ветку.

Порядок операций в этом случае особый: сначала добавляется новый торрент и проверяется, что qBittorrent его зарегистрировал, и только потом удаляется старый вместе с файлами. Иначе сбой при добавлении оставил бы вас без данных и без замены.

**Частичное обновление файлы не удаляет.** Если часть файлов совпала, а часть выбыла, убрать выбывшие нечем: qBittorrent умеет удалять только все файлы торрента сразу, а часть из них нужна новой версии. Сервис пишет в журнал, что осталось лежать на диске.

Удаление раздачи из отслеживания и откат не удаляют файлы ни при каких настройках.

## RuTracker

Это единственный поддерживаемый источник. Для ссылки вида:

```text
https://rutracker.org/forum/viewtopic.php?t=123456
```

resolver берёт topic id и скачивает:

```text
https://rutracker.org/forum/dl.php?t=123456
```

### Авторизация

Основной способ — логин и пароль на странице `Настройки`. Сервис входит на трекер сам и сохраняет cookie сессии; когда она истекает, он замечает это (вместо `.torrent` приходит страница) и входит заново, не требуя ничего от вас.

Вход выполняется браузером внутри FlareSolverr: перед формой стоит Cloudflare, обычным запросом её не пройти. Поэтому автоматический вход работает только со своим образом из этого compose-файла — со сторонним FlareSolverr придётся вставлять cookie вручную.

Кнопка `Проверить вход` на странице настроек выполняет вход немедленно и показывает результат — не нужно ждать ночной проверки, чтобы узнать, верен ли пароль.

Пароль хранится в базе открытым текстом, как и пароли qBittorrent.

Повторный вход не чаще, чем раз в `RUTRACKER_LOGIN_MIN_INTERVAL_SECONDS` (по умолчанию 5 минут): при неверном пароле сервис не должен долбить трекер. Кнопка в настройках это ограничение обходит — её нажал человек.

**Капча.** Трекер показывает её после неудачных попыток и при подозрительной активности с нового IP. Автоматически она не решается ничем. В этом случае сервис пишет об этом прямо, и нужно один раз войти в браузере и вставить cookie вручную:

```env
RUTRACKER_COOKIE=bb_session=...
```

Поле cookie есть и на странице `Настройки`, в блоке `Cookie вручную`. Туда же сервис складывает cookie, полученный автоматическим входом. Значение из настроек используется в первую очередь, `.env` остаётся fallback.

Нужна строка Cookie целиком: одного `cf_clearance` мало, это cookie Cloudflare, а не авторизация трекера. В строке должны быть `bb_session`, `bb_t` или `bb_data`.

### FlareSolverr

Если RuTracker показывает Cloudflare-проверку, скачать `.torrent` обычным HTTP-запросом нельзя. Для этого в `docker-compose.yml` поднимается второй контейнер, `torrent-watchdog-flaresolverr`.

Это **не стандартный образ FlareSolverr**. Он собирается из [Dockerfile.flaresolverr](Dockerfile.flaresolverr) и добавляет к обычному FlareSolverr endpoint `POST /download` ([flaresolverr-extended.py](flaresolverr-extended.py)): тот проходит проверку Cloudflare и скачивает файл прямо браузером через CDP `Page.setDownloadBehavior`. Стандартный FlareSolverr так не умеет — он возвращает только HTML страницы, а `dl.php` отдаёт бинарный файл.

Адрес и порт задаются на странице «Настройки» или в `.env`:

```env
FLARESOLVER_ADDRESS=http://flaresolverr
FLARESOLVER_PORT=8191
```

Имя хоста здесь имеет значение. Скачивание браузером включается, только если хост ровно `flaresolverr` — то есть при работе со своим контейнером из этого compose-файла. Любой другой адрес считается обычным FlareSolverr, и сервис работает по запасному пути: получает через него актуальные cookies и User-Agent, а затем скачивает `.torrent` обычным запросом. Запасной путь работает не на всех темах.

Пустой адрес отключает FlareSolverr — сервис скачивает напрямую по сохранённым cookie.

Не публикуйте FlareSolverr в интернете — он должен быть доступен только torrent-watchdog. В `docker-compose.yml` его порт наружу не выведен.

Секреты и passkey в URL маскируются в логах, пароль от трекера в них не попадает.

Если RuTracker временно не отвечает или возвращает не `.torrent`, resolver повторяет запрос — по умолчанию до трёх раз. Когда вместо файла приходит страница, это почти всегда истёкшая сессия: при заданных логине и пароле сервис входит заново прямо между попытками. Настройки:

```env
RUTRACKER_RETRY_DELAY_SECONDS=10
RUTRACKER_MAX_ATTEMPTS=3
```

`RUTRACKER_MAX_ATTEMPTS=0` означает повторять без ограничения, но для обычной эксплуатации лучше оставлять конечное число попыток. Иначе при DNS/сетевой проблеме ручная или плановая проверка может не завершиться. Если cookie не задан или resolver отключён, ошибка возвращается сразу, потому что повтор не сможет исправить конфигурацию.

## Восстановление после ошибки

Откройте карточку раздачи. Там отображается `last_error` и история событий. Можно:

- нажать `Проверить сейчас`;
- вручную применить найденную версию;
- применить одну из сохранённых старых версий из истории.

Rollback идёт тем же путём, что и обычное применение: удаляет текущий торрент из qBittorrent с `deleteFiles=false`, добавляет сохранённый старый `.torrent`, применяет режим обновления раздачи и обновляет текущий `info_hash`. Файлы на диске не удаляются.

Раздача, застрявшая в статусе `обновляется` из-за перезапуска сервиса во время применения, при следующем старте переводится в `ошибка` с объяснением в журнале.

## Журнал и логи

События проверок доступны на странице `Журнал` — последние 300 записей с фильтром по типу события и раздаче. Логи контейнера:

```bash
docker logs -f torrent-watchdog
```

В логах маскируются секретные параметры URL, например `passkey=***`. Cookie и пароли не выводятся.

## Данные

База SQLite:

```text
./data/app.db
```

Сохранённые `.torrent` файлы:

```text
./data/torrents/<tracked_id>/<info_hash>.torrent
./data/torrents/_pending/<info_hash>.torrent
```

`_pending` — временная папка: источник скачивается туда до того, как у раздачи появится `id`, после чего файл переносится. Если добавление сорвалось, файл остаётся там и удаляется уборкой.

В контейнере эти пути находятся в `/data`. При работе SQLite в режиме WAL рядом с базой лежат `app.db-wal` и `app.db-shm` — это нормально, для копии базы их нужно брать вместе с ней либо останавливать контейнер.

## Уведомления в Telegram

Бот пишет о том, что требует внимания: найдено обновление, обновление применено, ошибка проверки, qBittorrent недоступен. Сообщение выглядит так:

```text
🆕 Обновление найдено
   HOYO-MiX — Zenless Zero Zone OST [FLAC, 24 bit]

   Найдено обновление. Новых файлов: 3, уже были: 470, удалены из раздачи: 0.
```

У каждого типа события свой значок — 🆕 обновление, ✅ применено, ❌ не применилось, ⚠️ ошибка, 🔌 qBittorrent недоступен, — так что в списке чатов видно, что случилось, не открывая сообщение. Набор событий выбирается галочками на странице `Настройки`; рутинные проверки без изменений по умолчанию выключены, иначе бот писал бы дважды в день ни о чём.

Что нужно:

1. Создать бота у [@BotFather](https://t.me/BotFather) и получить токен.
2. Узнать ID чата — например, у [@userinfobot](https://t.me/userinfobot). Для группы ID начинается с минуса, и бота надо в неё добавить.
3. Вписать оба значения на странице `Настройки` и нажать `Отправить тестовое`: результат виден сразу, ждать ночной проверки не нужно.

```env
TELEGRAM_TOKEN=
TELEGRAM_CHAT_ID=
NOTIFY_LANGUAGE=ru
```

**Язык уведомлений задаётся отдельно** от языка интерфейса: у планировщика нет ни запроса, ни cookie, а читать сообщения может вообще другой человек. Список языков тот же, что и в интерфейсе, — новый язык подхватывается и здесь.

Отправка идёт в отдельном потоке и никогда не задерживает проверку. Если Telegram недоступен, проверка всё равно считается выполненной: молчащий бот — не повод считать раздачу непроверенной. Причина попадёт в лог контейнера предупреждением.

Токен хранится в базе открытым текстом, как пароли qBittorrent и трекера, и не показывается в форме: пустое поле означает «не менять».

## Язык интерфейса

Интерфейс есть на русском и английском. В шапке справа виден флаг и код текущего языка, по клику раскрывается список; выбор запоминается в cookie на год и не зависит от того, кто вошёл. Язык по умолчанию задаётся в `.env`:

```env
APP_LANGUAGE=ru
```

Переводится и журнал: в базу пишется код события и его параметры, а текст собирается при показе. Поэтому переключение языка меняет и старые записи, а не только меню. Записи, сделанные до появления переводов, разобраны обратно на коды по известным формулировкам; что разобрать не удалось, показывается так, как было записано.

### Как добавить язык

1. Скопируйте [app/locales/ru.py](app/locales/ru.py) в `app/locales/<код>.py` — например `de.py`.
2. Замените `NAME` на название языка, `FLAG` на флаг, `DATE_FORMAT` на привычный там формат даты и переведите значения. **Ключи менять нельзя** — по ним всё и находится.
3. Пересоберите образ: `docker compose up -d --build torrent-watchdog`.

Больше ничего не нужно: каталог `app/locales` сканируется при старте, язык сам появляется в переключателе. Регистрировать его в коде не требуется.

Флаг необязателен: без него язык получит значок глобуса. Переводить всё сразу тоже не обязательно — недостающие ключи берутся из русского каталога, страница не ломается. Полноту проверяет тест: он падает, если в каталоге не хватает ключей, есть лишние или в строке потерялся параметр вроде `{count}`.

Тексты ошибок и событий тоже живут в каталоге, отдельными ключами `error.*` и `msg.*`.

## Публикация образов

Собирает и выкладывает GitHub Actions по тегу версии:

```bash
git tag v0.7.6 && git push --tags
```

Workflow сверяет тег с файлом `VERSION` и отказывается публиковать при расхождении — иначе образ уедет под чужим номером. Дальше собирает оба образа под две архитектуры и пушит с тегами `0.7.6` и `latest`.

В секретах репозитория нужны `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` (токен создаётся в Docker Hub → Account Settings → Personal access tokens, прав `Read & Write` достаточно).

Собрать и запушить вручную можно и без CI:

```bash
docker buildx build --platform linux/amd64,linux/arm64 --push \
  -t roxelalex/torrent-watchdog:0.7.6 -t roxelalex/torrent-watchdog:latest .
docker buildx build --platform linux/amd64,linux/arm64 --push \
  -f Dockerfile.flaresolverr \
  -t roxelalex/torrent-watchdog-flaresolverr:0.7.6 \
  -t roxelalex/torrent-watchdog-flaresolverr:latest .
```

Чтобы запустить не свои образы, а чужие или локальные, задайте в `.env`:

```env
IMAGE_PREFIX=другой-аккаунт
IMAGE_TAG=0.7.5
```

## Тесты

```bash
docker run --rm -v "$PWD:/src:ro" -w /tmp/proj python:3.12-slim \
  sh -c "cp -r /src/. /tmp/proj && pip install -q -r requirements-dev.txt && python -m pytest -q"
```

Покрыты: расчёт `info_hash`, сравнение состава файлов между версиями, выбор версии, ожидающей применения, разрешение путей категорий, выбор категории и полнота переводов.

Скрипт страницы проверяется отдельно — синтаксис и то, что он переживает загрузку:

```bash
docker run --rm -v "$PWD:/src:ro" -w /src node:22-slim \
  sh -c "node --check app/static/app.js && node tests/js/smoke.js /src/app/static/app.js"
```

Проверка на загрузку не формальность: обращение к `const` до его объявления роняет весь файл, и страница молча остаётся без интерактива, а `node --check` этого не видит.
