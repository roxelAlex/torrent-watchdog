# torrent-watchdog

Веб-сервис для отслеживания обновлений раздач RuTracker. Под наблюдение берётся ссылка на тему; сервис сохраняет текущий `info_hash`, скачивает с темы свежий `.torrent` по расписанию и показывает найденные обновления. Если включён `auto_update`, он заменяет торрент в удалённом qBittorrent: ставит старый торрент на паузу, удаляет его из qBittorrent с `deleteFiles=false`, добавляет новый `.torrent` в тот же `save_path`, восстанавливает категорию и теги и применяет выбранный режим обновления. Файлы на диске не удаляются никогда.

Версия: `0.4.0`. Полный список изменений — в [CHANGELOG.md](CHANGELOG.md).

## Запуск

```bash
cp .env.example .env
docker compose up -d --build
```

Поднимаются два контейнера: `torrent-watchdog` и `torrent-watchdog-flaresolverr` (свой образ, см. раздел про FlareSolverr).

Откройте веб-интерфейс:

```text
http://SERVER_IP:8096
```

Вход — форма на `/login`, логин и пароль из `.env`:

```text
admin / change_me
```

Перед постоянным использованием смените в `.env` две вещи, а не одну:

- `APP_AUTH_PASSWORD` — пароль;
- `APP_SECRET_KEY` — им подписывается cookie сессии. С дефолтным значением сессию можно подделать, не зная пароля.

`APP_AUTH_ENABLED=false` полностью отключает вход. Так можно, если сервис доступен только из доверенной сети, но порт по умолчанию публикуется на всех интерфейсах.

HTTP Basic принимается как запасной способ авторизации для `/api/*` — это удобно для скриптов, веб-интерфейс им не пользуется.

## Настройка .env

Полный список переменных со значениями по умолчанию — в [.env.example](.env.example). Ключевые:

```env
APP_PORT=8096
TZ=Asia/Yekaterinburg
DATABASE_URL=sqlite:////data/app.db

QB_HOST=http://192.168.0.220:8090
QB_USERNAME=admin
QB_PASSWORD=adminadmin

CHECK_HOUR=4
CHECK_MINUTE=0
CHECK_MAX_WORKERS=3

EVENT_RETENTION_DAYS=180
TORRENT_FILE_RETENTION_DAYS=30

APP_AUTH_ENABLED=true
APP_AUTH_USERNAME=admin
APP_AUTH_PASSWORD=change_me
APP_SECRET_KEY=change_me_random_secret

RUTRACKER_ENABLED=true
RUTRACKER_COOKIE=
FLARESOLVER_ADDRESS=http://flaresolverr
FLARESOLVER_PORT=8191
```

Если меняете `APP_PORT`, docker-compose пробросит тот же порт наружу и внутрь контейнера.

`QB_HOST`, `QB_USERNAME` и `QB_PASSWORD` читаются только один раз — при создании клиента `Основной` в пустой базе. Дальше клиенты правятся на странице «Настройки», и правка `.env` на них уже не влияет.

`RUTRACKER_COOKIE`, `FLARESOLVER_ADDRESS` и `FLARESOLVER_PORT` — значения по умолчанию: то, что сохранено на странице «Настройки», имеет приоритет.

Сервис должен работать ровно в один процесс uvicorn. Планировщик живёт внутри процесса, поэтому второй воркер означал бы вторую ежедневную проверку: параллельные скачивания одной раздачи и гонку при применении обновления.

## qBittorrent на другой ВМ

qBittorrent не запускается внутри `docker-compose.yml` этого проекта. Он должен быть доступен по HTTP через Web API на другой ВМ или хосте.

Не используйте `localhost` или `127.0.0.1` в `QB_HOST`: внутри Docker-контейнера это будет сам контейнер `torrent-watchdog`, а не ВМ с qBittorrent.

Настройка qBittorrent на другой ВМ:

1. В qBittorrent включить Web UI.
2. Убедиться, что Web UI доступен по IP ВМ, а не только на `127.0.0.1`.
3. Проверить порт, например `8090`.
4. На ВМ с qBittorrent открыть порт в firewall.
5. В `.env` сервиса `torrent-watchdog` указать:

```env
QB_HOST=http://192.168.0.220:8090
QB_USERNAME=ваш_логин
QB_PASSWORD=ваш_пароль
```

6. Проверить доступность с сервера:

```bash
curl -I http://192.168.0.220:8090
```

7. Если сервис запущен в Docker, проверить из контейнера:

```bash
docker exec -it torrent-watchdog sh
wget -S -O- http://192.168.0.220:8090
```

Пользователь из `QB_USERNAME` должен иметь право добавлять, удалять, ставить на паузу, запускать и recheck торренты.

Для qBittorrent 5.x сервис автоматически использует новые endpoints `stop/start`, если старые `pause/resume` недоступны.

Проверить подключение можно кнопкой `Проверить всех` на странице `Настройки` — она опрашивает все настроенные клиенты. Там же можно добавить несколько qBittorrent-клиентов, выбрать основной клиент и затем выбирать нужный клиент при добавлении раздачи.

Статусы клиентов кэшируются на несколько секунд, поэтому страницы не ждут ответа от недоступного клиента при каждом открытии. Кнопка `Проверить всех` опрашивает клиенты заново, минуя кэш.

При первом запуске создаётся клиент `Основной` из переменных `QB_HOST`, `QB_USERNAME`, `QB_PASSWORD`. Уже добавленные раздачи автоматически привязываются к нему.

Категории qBittorrent автоматически подгружаются на странице добавления раздачи и доступны через API:

```text
GET /api/qbittorrent/categories
GET /api/qbittorrent/clients
```

Если qBittorrent недоступен, приложение всё равно запускается. `/health` покажет статус qBittorrent, а операции добавления или обновления завершатся ошибкой в интерфейсе и в `check_events`.

## Добавление первой раздачи

Под наблюдение берутся только темы RuTracker:

```text
https://rutracker.org/forum/viewtopic.php?t=123456
```

Magnet и прямые ссылки на `.torrent` не принимаются — форма и API отклонят их с подсказкой. Смысл в том, что тема остаётся постоянным адресом: с неё каждый раз скачивается свежий `.torrent`, и есть с чем сравнить состав файлов. У magnet файла раздачи нет вовсе, а его `info_hash` неизменен, так что обновление по нему не обнаружить в принципе.

Откройте `Добавить` и заполните:

- ссылку на тему RuTracker;
- путь загрузки `save_path`;
- категорию и теги при необходимости;
- параметры `auto_update`, `recheck_after_add`, `start_after_recheck`, `add_paused`.

После добавления сервис скачает `.torrent` с темы, рассчитает `info_hash`, добавит торрент в qBittorrent и создаст первую запись истории версий.

## Проверка обновлений

Планировщик запускается ежедневно в `CHECK_HOUR:CHECK_MINUTE` с timezone из `TZ`. Расписание применяется при перезапуске контейнера; на странице «Настройки» оно показано, но не редактируется.

Ручная проверка — кнопка `Проверить` в реестре и `Проверить сейчас` в карточке раздачи.

Раздачи проверяются параллельно, до `CHECK_MAX_WORKERS` одновременно. Обращения к FlareSolverr при этом идут строго по очереди: браузер в контейнере один, и два одновременных вызова Cloudflare не решаются оба.

Если `info_hash` не изменился, статус остаётся `active`. Если изменился, создаётся новая версия и статус становится `update_available`.

После ночной проверки выполняется уборка: удаляются события старше `EVENT_RETENTION_DAYS` и `.torrent`-файлы старше `TORRENT_FILE_RETENTION_DAYS`, на которые не ссылается ни одна версия. Оба значения можно обнулить, чтобы отключить уборку.

## Auto update

Если у раздачи включён `auto_update`, найденная новая версия применяется автоматически:

1. старый торрент ставится на паузу;
2. старый торрент удаляется из qBittorrent с `deleteFiles=false`;
3. новый `.torrent` добавляется в тот же `save_path`;
4. назначаются прежние категория и теги;
5. применяется выбранный режим обновления;
6. торрент запускается, если включено.

Доступны два режима:

- `Скачивать только новые файлы` - режим для медиатеки. Сервис сравнивает старый и новый `.torrent`, старые файлы в новом torrent помечает как `не скачивать`, новые оставляет выбранными. `recheck` не запускается, чтобы qBittorrent не перекачивал файлы, в которые уже записаны теги.
- `Полная замена с проверкой файлов` - классический режим: добавить новый torrent и запустить recheck. qBittorrent сверит уже лежащие на диске файлы и докачает только недостающее.

Если сохранённый `.torrent` прошлой версии недоступен, сравнить состав файлов не с чем. В этом случае режим `только новые файлы` не выставляет приоритеты, а запускает recheck: иначе qBittorrent считал бы, что на диске пусто, и скачал бы раздачу заново. В журнале об этом пишется явно.

## Почему файлы не удаляются

Проект никогда не удаляет файлы раздачи с диска. Вызов qBittorrent delete API централизован в `app/services/qbittorrent_client.py`, и параметр `delete_files` по умолчанию равен `False`. Обновление и rollback явно вызывают удаление с `delete_files=False`.

Кнопка `Убрать из отслеживания` удаляет только запись из базы вместе с историей версий и событий. Торрент в qBittorrent и файлы на диске остаются на месте.

## RuTracker

Это единственный поддерживаемый источник. Для ссылки вида:

```text
https://rutracker.org/forum/viewtopic.php?t=123456
```

resolver берёт topic id и скачивает:

```text
https://rutracker.org/forum/dl.php?t=123456
```

Для скачивания нужен `RUTRACKER_COOKIE`. Вставьте cookie авторизованной сессии в `.env`:

```env
RUTRACKER_COOKIE=bb_session=...
```

Cookie также можно вставить на странице `Настройки`. Значение из страницы настроек используется в первую очередь, `.env` остаётся fallback.

### FlareSolverr

Если RuTracker показывает Cloudflare-проверку, скачать `.torrent` обычным HTTP-запросом нельзя. Для этого в `docker-compose.yml` поднимается второй контейнер, `torrent-watchdog-flaresolverr`.

Это **не стандартный образ FlareSolverr**. Он собирается из [Dockerfile.flaresolverr](Dockerfile.flaresolverr) и добавляет к обычному FlareSolverr endpoint `POST /download` ([flaresolverr-extended.py](flaresolverr-extended.py)): тот проходит проверку Cloudflare и скачивает файл прямо браузером через CDP `Page.setDownloadBehavior`. Стандартный FlareSolverr так не умеет — он возвращает только HTML страницы, а `dl.php` отдаёт бинарный файл.

Адрес и порт задаются на странице «Настройки» или в `.env`:

```env
FLARESOLVER_ADDRESS=http://flaresolverr
FLARESOLVER_PORT=8191
```

Имя хоста здесь имеет значение. Скачивание браузером включается, только если хост ровно `flaresolverr` — то есть при работе со своим контейнером из этого compose-файла. Любой другой адрес считается обычным FlareSolverr, и сервис работает по запасному пути: получает через него актуальные cookies и User-Agent, а затем скачивает `.torrent` обычным запросом. Запасной путь работает не на всех темах.

Пустой адрес отключает FlareSolverr — сервис скачивает напрямую по сохранённым cookie.

Не публикуйте FlareSolverr в интернете — он должен быть доступен только torrent-watchdog. В `docker-compose.yml` его порт наружу не выведен.

Важно: одного `cf_clearance` недостаточно. Это cookie Cloudflare, а не авторизация RuTracker. В строке должны быть авторизационные cookie RuTracker, например `bb_session`, `bb_t` или `bb_data`.

Секреты и passkey в URL маскируются в логах.

Если RuTracker временно не отвечает или возвращает не `.torrent`, resolver повторяет запрос — по умолчанию до трёх раз. Настройки:

```env
RUTRACKER_RETRY_DELAY_SECONDS=10
RUTRACKER_MAX_ATTEMPTS=3
```

`RUTRACKER_MAX_ATTEMPTS=0` означает повторять без ограничения, но для обычной эксплуатации лучше оставлять конечное число попыток. Иначе при DNS/сетевой проблеме ручная или плановая проверка может не завершиться. Если cookie не задан или resolver отключён, ошибка возвращается сразу, потому что повтор не сможет исправить конфигурацию.

## Восстановление после ошибки

Откройте карточку раздачи. Там отображается `last_error` и история событий. Можно:

- нажать `Проверить сейчас`;
- вручную применить найденную версию;
- применить одну из сохранённых старых версий из истории.

Rollback идёт тем же путём, что и обычное применение: удаляет текущий торрент из qBittorrent с `deleteFiles=false`, добавляет сохранённый старый `.torrent`, применяет режим обновления раздачи и обновляет текущий `info_hash`. Файлы на диске не удаляются.

Раздача, застрявшая в статусе `обновляется` из-за перезапуска сервиса во время применения, при следующем старте переводится в `ошибка` с объяснением в журнале.

## Журнал и логи

События проверок доступны на странице `Журнал` — последние 300 записей с фильтром по типу события и раздаче. Логи контейнера:

```bash
docker logs -f torrent-watchdog
```

В логах маскируются секретные параметры URL, например `passkey=***`. Cookie и пароли не выводятся.

## Данные

База SQLite:

```text
./data/app.db
```

Сохранённые `.torrent` файлы:

```text
./data/torrents/<tracked_id>/<info_hash>.torrent
./data/torrents/_pending/<info_hash>.torrent
```

`_pending` — временная папка: источник скачивается туда до того, как у раздачи появится `id`, после чего файл переносится. Если добавление сорвалось, файл остаётся там и удаляется уборкой.

В контейнере эти пути находятся в `/data`. При работе SQLite в режиме WAL рядом с базой лежат `app.db-wal` и `app.db-shm` — это нормально, для копии базы их нужно брать вместе с ней либо останавливать контейнер.
